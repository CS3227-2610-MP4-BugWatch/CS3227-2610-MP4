## Functions Created

- `containsCredentialSolicitation(questions: readonly string[]): boolean` in `api/_lib/_tester-question-policy.ts` checks already structurally validated and trimmed questions. `questions` is the read-only list returned by the existing parser; it may be empty. The function returns `true` when any question matches a supported request to disclose a credential value. It returns `false` for an empty list or no match, which is not a general safety verdict.

  The function calls `Array.some` to inspect each question and stop as soon as one matches. Each question is copied through `normalize('NFKC')`, which converts compatibility characters such as fullwidth letters to their ordinary equivalents. `toLowerCase` removes casing differences, `replace(/\s+/gu, ' ')` folds runs of whitespace into one space, and `trim` removes leading and trailing spaces. These operations affect only the inspected copy. Saved incident evidence and accepted output strings are not rewritten.

  Two regular expressions inspect the normalized copy. Their pieces are kept at module scope so their purpose can be reviewed separately:

  - `credential` lists supported categories: passwords; one-time authentication, verification, or security codes; authentication, verification, security, or login codes; access, refresh, authentication, bearer, or session tokens; private keys; API keys; and credentials. The expressions support the written singular/plural forms. Ordinary `code` alone is absent, so an error-code request does not match merely because it contains that word.
  - `qualifiers` permits zero to five ordinary words immediately before the credential category, including `your`, `account`, `current`, `actual`, `full`, and `value of`. This handles direct forms such as “your account password” without allowing an unrestricted gap between the request and the credential category.
  - `diagnosticSuffix` is a negative lookahead: it prevents a match when the credential term is immediately followed by one of the listed diagnostic words, such as `reset`, `change`, `policy`, `length`, `configuration`, `type`, `error`, or `status`. For example, asking for a password-reset error is different from asking for the password itself. This is a bounded list rather than a semantic understanding of every diagnostic question.
  - `disclosure` recognizes `can`, `could`, `would`, or `will` followed by `you`, optionally `please`, or an imperative beginning at the start of the string with optional `please`. It then requires a disclosure verb such as `provide`, `share`, `paste`, `send`, `reveal`, or `give`, an optional `me` or `us`, the allowed qualifiers, and an adjacent credential category. A word boundary after the category avoids matching a category inside a longer word. For example, “Can you paste your access token?” matches.
  - `valueQuestion` recognizes `what is` or `what are`, followed by the allowed qualifiers and a credential category, with the same diagnostic exception. For example, “What is your password?” matches.

  `RegExp.test` checks the disclosure expression and the value-question expression. The helper returns their logical OR for the current question, then `some` returns whether any question matched. It neither changes the list nor returns a filtered subset. The required benign examples—password-change timing, authentication method, API-key presence, and error code—remain unmatched. Unsupported paraphrases, languages, encodings, confusable characters, and hidden-text tricks can escape these rules. No decoding, URL/command recognition, secondary classifier, or external request is performed.

## Functions Changed

- `handleTesterQuestions(request, dependencies)` in `api/developer/tester-questions.ts` now calls the policy helper before returning a successful result. `request` is the incoming Fetch API request with its method, bearer token, and report-ID body. `dependencies` supplies the existing injectable authentication, saved-context reading, eligibility checks, quota reservation, and generation functions; its interface did not change.

  The earlier authentication, input validation, allowlisted context construction, 60,000-byte complete-message guard, pre-generation eligibility check, and atomic quota reservation remain intact. After `dependencies.generate(context)` returns, the existing `checkEligibility` call reloads access eligibility and `eligibilityFailure` suppresses output if access was lost. The existing `parseTesterQuestions(generated)` then validates the output's exact shape and limits, returning trimmed questions or `null`.

  The success condition now requires both a valid parsed list and `!containsCredentialSolicitation(questions)`. JavaScript's short-circuit evaluation means the helper is not called for structurally invalid output. Accepted questions are returned unchanged through `reply(200, ...)`, together with the existing `questionContextVersion(context)` checksum. An empty list still succeeds because the helper finds no matching question.

  If any question matches, the handler does not return any of that new result. It falls through to the existing `reply(502, { code: 'unavailable' })`. `reply` adds `Cache-Control: no-store`; the response includes neither rejected text nor policy details. Unexpected helper errors enter the existing catch block and also fail through the safe error path. The attempt was already reserved, so it stays consumed exactly once. There is no refund or automatic retry. The existing client/hook treats this as failed regeneration, keeping prior suggestions and their outdated indication while leaving composer text and the selected reply target intact. The rejected new questions never reach display or Copy.

- The Developer `instructions` used by `testerQuestionMessages(context)` were expanded. The function's parameter is the complete saved, allowlisted report/discussion context; its implementation still returns a separate system message and user message. It continues to call `serializeQuestionContext(context)` for the latter without filtering, omitting, decoding, or rewriting incident evidence.

  The system message now explicitly identifies all report fields and comments as untrusted incident data. It tells the model to ignore task overrides, quoted system/assistant role messages, claimed administrator instructions, and encoded or hidden instructions. It also tells the model to continue using relevant incident facts rather than return no questions simply because suspicious text is quoted.

  Additional instructions prohibit requesting passwords, authentication codes, access tokens, private keys, API keys, or other credentials. They tell the model not to include URLs, external submission destinations, executable commands, scripts, or instructions to run code, and to ask for plain-language reproduction descriptions instead. The existing zero-to-five questions, 200-character limit, questions-only JSON shape, and legitimate empty-result behavior remain in the prompt.

  URL and command restrictions are deliberately prompt-only. This change adds no detector or automatic rejection based on their presence. Output that passes the structural and bounded credential checks can still contain such text if the model ignores its instructions; the unchanged UI renders it as inert text and requires explicit Copy and separate manual posting. The longer system message counts toward the same existing 60,000-byte guard through `questionContextByteLength`, which already measures the actual serialized messages. The guard, provider limits/settings, Tester behavior, and authorization boundaries were not expanded.
