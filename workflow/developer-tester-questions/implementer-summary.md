## Files Added

- `api/_lib/_tester-question-dependencies.ts` supplies the endpoint's real Supabase authentication, report/discussion reads, quota reservation, eligibility rechecks, and SoCLaaS call. It keeps credentials and model settings on the server.
- `src/features/reports/testerQuestionTypes.ts` defines the request/result and allowlisted context types. Its helpers select incident fields, serialize them consistently, calculate a context checksum, and validate question arrays.

- `src/features/reports/useTesterQuestions.ts` manages temporary questions, pending requests, retry feedback, and stale-context comparison without saving output to persistent storage.
- `src/features/reports/database/013_developer_question_quota.sql` creates separate Developer quota storage and a service-role-only reservation function. ## Functions Created

- `requestSoCLaaS(apiKey, model, messages, options)` in `api/_lib/_soclaas.ts` makes the shared provider request. `apiKey` authenticates the server, `model` selects the configured model, and `messages` holds the trusted system message and serialized incident data. `options` supplies the timeout and token cap, plus optional temperature and top-p. The function calls `fetch` with redirects rejected, streaming disabled, reasoning disabled, and `AbortSignal.timeout` to bound the provider call. Optional sampling keys are included only when supplied. On success it reads the first response message and parses its JSON content. HTTP 413 and recognized context-window error codes become `SoCLaaSContextTooLarge`; other failures throw a generic error. The endpoint converts these errors into safe public responses.

- `testerQuestionMessages(context)` in `api/developer/tester-questions.ts` builds the two provider messages. `context` contains the saved report fields and complete ordered discussion. The first message gives the server-selected questions-only rules and treats incident text as untrusted data. The second calls `serializeQuestionContext` to include only the allowed fields. It does not accept prompts or sampling settings from the browser.

- `questionContextByteLength(context)` in the same endpoint measures the exact serialized provider-message array. It calls `testerQuestionMessages`, converts the JSON string to UTF-8 with `TextEncoder`, and returns the byte count. The handler admits exactly 60,000 bytes and refuses larger input before reserving quota.

- `questionEligibility(context, actorId)` in the same endpoint checks ownership and report status. `context` includes the loaded assignment, state, and archive flag; `actorId` is the authenticated Developer's ID. It compares IDs without case sensitivity, rejects a different or absent assignee as forbidden, and rejects archived projects or states outside Accepted, In progress, and Awaiting tester information as ineligible. Otherwise it returns `eligible`.

- `readReportId(request)` in the same endpoint reads and validates the HTTP body. `request` is the incoming Fetch API request. It reads chunks through the body's reader, counts bytes, and cancels reading when the body exceeds 4,096 bytes. A fatal UTF-8 decoder prevents invalid byte sequences from becoming valid input. After reading, it parses JSON, requires an object with a string `reportId`, trims that ID, and checks `REPORT_UUID`. Extra properties are ignored. Invalid input returns `null`, and the reader lock is released in all cases.

- `reply(status, body, headers)` in the same endpoint creates JSON responses. `status` is the HTTP status, `body` is the safe public payload, and optional `headers` carries values such as `Allow` or `Retry-After`. It always adds `Cache-Control: no-store` so generated questions and errors are not cached.

- `eligibilityFailure(eligibility)` in the same endpoint translates an eligibility result into an HTTP response. It returns `null` for an eligible report; otherwise it calls `reply` with 403, 404, or 409 and the matching safe error code.

- `handleTesterQuestions(request, dependencies)` in the same endpoint coordinates generation. `request` supplies the method, bearer token, and report ID. `dependencies` provides injectable authentication, context loading, eligibility checks, reservation, and generation functions. The handler first enforces POST and bearer authentication, then requires the Developer role and a valid report ID. It loads saved context, checks assignment/state/archive, and calls `questionContext` to remove metadata. It refuses oversized messages, rechecks current eligibility, and reserves one attempt using the server-derived actor ID. A denied reservation returns 429 with a positive retry interval. An admitted request calls the generator, rechecks eligibility before exposing output, and calls `parseTesterQuestions`. A valid result, including an empty list, is returned with `questionContextVersion`. Database/provider details are suppressed; context-size failures return 413 and other failures return a safe 502. Admitted failed and empty attempts remain consumed. The handler never posts comments or changes reports.

- The endpoint's default `fetch(request)` entry point enforces the method before loading configuration. It calls `createTesterQuestionDependencies(process.env)` and delegates to the injectable handler only when configuration is enabled and complete. Disabled, missing, or invalid configuration returns a no-store 503 response without reserving quota or dispatching a provider request.

- `createTesterQuestionDependencies(env)` in `api/_lib/_tester-question-dependencies.ts` constructs the real server dependencies. `env` is the server environment. The function reads the independent Developer enablement flag, Supabase URL/keys, provider key, and model, returning `null` when required settings are absent. Its local `userClient(token)` helper creates a stateless Supabase client using the caller's bearer token. A separate service-role client is used only for quota reservation.
  - `authenticate(token)` calls Supabase `auth.getUser` to validate the token, then reads the saved profile role. Missing/invalid authentication returns `null`; unexpected auth or profile-read failures throw.
  - `loadContext(token, reportId)` creates the existing report repository with the authorized client. It calls `getReport`, then `listReportComments`, which already reads and validates every comment page in chronological order with IDs breaking timestamp ties. A missing report returns `null`; a failed or incomplete read throws. `questionContext` strips profile/project metadata from the model data, while assignment/state/archive remain separate for authorization.
  - `checkEligibility(token, reportId, actorId)` authenticates again, checks the same Developer identity and role, reloads the current report, and calls `questionEligibility`. It does not assume that the initial assignment or role is still valid after generation.
  - `reserve(actorId)` calls `reserve_developer_question_attempt` with the authenticated ID. It rejects RPC errors and malformed results, including invalid retry intervals, so quota failures do not allow a provider call.
  - `generate(context)` calls `requestSoCLaaS` with `testerQuestionMessages(context)`, a 15,000-millisecond timeout and 1,500-token cap, temperature 0.7, and top-p 0.8. The shared transport supplies disabled reasoning. These initially tentative settings were retained after the user-reported live operational review described above.

- `questionContext(context)` in `testerQuestionTypes.ts` creates a fresh object containing only title, description, version, reproduction steps, expected/actual results, severity, environment, and each comment's ID, text, and reply reference. Its input may contain additional report metadata, but the returned object does not. It preserves the reader's established chronological comment order.

- `serializeQuestionContext(context)` in the same module calls `questionContext` and serializes the result with `JSON.stringify`. Explicit field construction makes server and browser snapshots use the same field order and excludes unsent composer text.

- `questionContextVersion(context)` in the same module calls that serializer, encodes the result as UTF-8, and calculates a deterministic 64-bit FNV-1a checksum. It returns a padded hexadecimal string rather than report text. The checksum detects changed context; it is not cryptographic authorization evidence and is never used to grant access.

- `parseTesterQuestions(value)` in the same module validates untrusted decoded output. `value` may have any shape. The function requires an object with exactly one `questions` key and an array containing at most five strings. Each string is trimmed, must remain nonblank, and must contain at most 200 Unicode code points. Any invalid element rejects the whole result with `null`; an explicit empty array is valid.

- `TesterQuestionError(code, retryAfterMs)` in `testerQuestionClient.ts` carries a safe server error code and an optional wait duration. Its message is generic. The hook uses those properties to select feedback without showing internal provider or database messages.

- `requestTesterQuestions(request, signal)` in that client accepts the report-ID DTO and the current request's abort signal. It imports the shared Supabase client, gets the current session, and checks cancellation before making the request. It sends only `reportId` and the bearer token to `/api/developer/tester-questions`. Error responses become `TesterQuestionError`; positive rate-limit waits are capped at five minutes. Successful responses must contain a nonempty context version and a question list accepted by `parseTesterQuestions`. It returns those validated values to the hook.

- `failureMessage(error)` in `useTesterQuestions.ts` turns an error into user-facing feedback. It gives specific explanations for oversized full context, expired authentication, and quota limits, with a generic manual-discussion fallback for other failures.

- `createTesterQuestionSession()` in the same hook module creates the page's in-memory state and request controls. It takes no parameters and returns methods used by React through `useSyncExternalStore`.
  - `update(patch)` merges changed state fields into a new object and notifies subscribers.
  - `clear()` aborts the active request, clears its retry timer, and discards questions, pending state, and feedback.
  - `getSnapshot()` returns the current state; `subscribe(listener)` registers a React update callback. When the final subscriber leaves, a queued microtask clears the session unless Strict Mode has immediately resubscribed.
  - `setContext(contextVersion)` stores the latest successfully loaded snapshot version only when it changes. This retains the last known version while discussion is temporarily reloading.
  - The session's `generate(generate, reportId)` receives the injected request function and current report ID. It refuses overlapping or cooling-down requests, creates an `AbortController`, and marks generation pending. Success saves the returned questions only if the request was not aborted. Failure retains prior questions except when an authorization or eligibility error means they must be cleared. Rate-limit errors start a timer that later re-enables generation. The final step clears pending state for the completed request without triggering an automatic retry.

- `useTesterQuestions(generate, reportId, eligible, contextVersion)` connects that session to the page. `generate` is the real or injected API function, `reportId` identifies the current report, `eligible` reflects the loaded user's access, and `contextVersion` represents successfully loaded saved data. The hook subscribes to session updates, clears output when eligibility is lost, and records newly loaded versions. It compares the returned server version against the current or last loaded version to label old questions outdated. Its returned generation action requires eligibility, a report ID, and complete loaded context.

- `copyQuestion(text)` inside `ReportDetails` receives one generated question and calls `navigator.clipboard.writeText`. Success tells the Developer to paste and edit it manually. Clipboard failure leaves the displayed text available for selection and gives safe feedback. It never changes composer text, reply selection, report fields, or discussion state.

- `reserve_developer_question_attempt(p_actor_id)` in migration 013 implements the intended database reservation. `p_actor_id` is supplied by the trusted server. The function verifies that the saved profile has the Developer role, creates its quota row if necessary, and locks that row before reading server time. It removes attempts at least five minutes old. Five remaining attempts produce a denial and a positive wait until the earliest expires; otherwise the current server timestamp is appended and admission returns a zero wait. The migration enables RLS, revokes direct table access, and grants function execution only to the service role. Tester quota storage and functions are unchanged. This explains the source behavior. Local SQL cases were historically skipped; later the user reported separate quota tests passed, accepted by VERIFY-USER-4. The agent did not execute SQL or receive individual permissions, expiry, or concurrency console results.

## Functions Changed

- `createSoCLaaSGenerator(apiKey, model)` in `api/_lib/_soclaas.ts` now calls `requestSoCLaaS` instead of repeating the HTTP implementation. It still receives the server provider key and configured model and returns the existing Tester generator. It supplies the unchanged Tester system prompt, serializes the same Tester context, and passes the original timeout/token settings without Developer sampling options.

- `ReportDetails` in `src/features/reports/ReportDetailsPage.tsx` now accepts optional `generateTesterQuestions`, defaulting to `requestTesterQuestions`. Its existing `reportRepository`, `user`, and `reportId` parameters continue to control report/discussion loading and manual actions. After existing reads, it derives question eligibility from the Developer role, active project, current assignment, and allowed states. When comments are fully loaded it calculates `questionContextVersion` and calls `useTesterQuestions`. The page renders explicit generation controls, read-only output, empty/error/outdated feedback, and per-question Copy actions. Discussion loading failures disable generation instead of supplying empty context. Existing report/account keyed mounting recreates the page session when navigation or identity changes, preventing late results from filling another screen. Existing posting and workflow handlers remain separate. UI-1 later styled this section and its controls without changing those contracts.

- No repository method behavior was changed. `createReportRepository` is reused by the new server composition for its existing validated report reads and complete comment pagination; only the module's local import extensions changed.
