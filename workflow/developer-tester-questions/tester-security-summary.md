## Test Cases Added

The names below are the source titles. Vitest replaces `%s` with the selected question and `%d` with the selected number. `$variant` is the label from a parameterized object. The steps describe the statements in each test in their execution order.

### Pure policy tests

All cases in this subsection are in `src/test/developer-tester-questions-policy.test.ts`. The helper accepts an array of already validated question strings; `true` means at least one matches the bounded credential-disclosure rules. It does not return a filtered list or classify all malicious language.

The `solicitations` fixture contains six exact I4 examples: asking for a password, account password, one-time authentication code, access token, private key, or API key. The `diagnostics` fixture contains four benign examples: behavior after changing a password, authentication method, whether an API key is configured, and an error code. `fullwidth(text)` walks through the input's characters, converts printable ASCII characters to their fullwidth Unicode equivalents, leaves other characters alone, and joins the result. It only builds test input; it does not alter production context.

- `credentialPolicy_explicitDisclosure%s_matches` runs six cases. The scenario is a direct request for a secret value. Each test passes its `question` inside a one-item array to the policy and asserts `true`. For example, `Can you paste your access token?` must match.
- `credentialPolicy_benignDiagnostic%s_doesNotMatch` runs four cases. Each passes a diagnostic question to the helper and asserts `false`. For example, `Could you provide the error code?` asks for ordinary diagnostic data and must remain allowed.
- `credentialPolicy_$variantExplicitDisclosure_normalizesAndMatches` runs 18 cases. `flatMap` makes three variants of each of the six positive examples: uppercase, tabs/newlines/repeated spaces with surrounding whitespace, and fullwidth text. The callback receives the generated `question`, calls the helper with it, and expects `true`. For example, an uppercase access-token request or a fullwidth password request must still match.
- `credentialPolicy_$variantBenignDiagnostic_remainsAllowed` runs 12 cases. It creates the same three variants for each benign example, calls the helper, and expects `false`. For example, spacing or fullwidth letters must not turn `Is an API key configured?` into a refusal.
- `credentialPolicy_emptyQuestions_doesNotMatch` considers a valid empty model result. It calls the helper with `[]` and expects `false`; absence of useful questions is not a policy violation.
- `credentialPolicy_solicitationAtIndex%d_matchesEntireList` runs three cases with `index` equal to 0, 1, or 2. It first makes three benign questions, replaces the selected entry with `What is your password?`, calls the helper, and expects `true`. This verifies that a match is found at the beginning, middle, or end rather than only in the first item.
- `credentialPolicy_readonlyInput_doesNotRewriteQuestions` freezes a list containing a partly fullwidth API-key request and an error-code question. It copies that list before calling the helper, checks that the solicitation matches, and then compares the frozen list to the original copy. The expected behavior is detection without rewriting the caller's accepted text.
- `credentialPolicy_nonSolicitingText%s_hasNoUrlCommandOrKeywordFilter` runs six cases: the individual words password/token/code, a harmless example URL, a harmless `echo diagnostic` command reference, and a literal script-tag description. Each goes into a one-item list and must return `false`. These cases verify the explicit scope exclusion; they do not mean such model output follows the prompt or is safe in every setting.

### Endpoint policy integration tests

These cases are in `src/test/developer-tester-questions-api.test.ts`. The existing `setup()` makes successful authentication, saved-context, eligibility, quota, and generation mocks. Its `request()` constructs a POST Request for a valid report and invokes the actual handler. A test replaces only the relevant generated output or dependency. Cleanup restores spies and environment/global changes after each case.

- `testerQuestions_explicitCredentialDisclosure%s_rejectsWholeResultSafelyAfterOneAttempt` runs 24 cases. Six exact solicitations are each tested unchanged, uppercase, with folded whitespace, and as fullwidth characters. The callback receives that `question`, creates the normal dependency fixture, and makes generation return a benign browser question together with the solicitation. It awaits the handler, checks HTTP 502 and no-store caching, and requires the entire JSON body to equal `{ code: 'unavailable' }`. It then checks exactly one reservation for the trusted actor, one generation call, and both eligibility checks. For example, a result containing `Which browser version?` and `Could you send your private key?` must disclose neither question, return no allowed subset, consume one attempt, and make no automatic retry.
- `testerQuestions_benignCredentialQuestion%s_preservesAcceptedText` runs 16 cases: four benign examples in the same four forms. It makes generation return the selected single question, invokes the handler, checks HTTP 200 and the exact returned text/context version, and checks one reservation. For example, `COULD YOU PROVIDE THE ERROR CODE?` must be accepted without lowercasing its displayed text. The response comparison verifies that normalization used for checking does not rewrite accepted output.
- `testerQuestions_credentialPolicyException_failsClosedWithoutExposingDetails` creates normal mocks, then uses `vi.spyOn` to replace the policy with a function that throws a private error. It invokes the handler, checks safe HTTP 502 JSON, and checks one reservation and one generation call. The example failure is `private policy details`; that text must not appear in the response.
- `testerQuestions_eligibilityLostBeforeOutputPolicy_keepsAuthorizationDenial` records policy calls with a spy. Its generation mock changes the following eligibility result to forbidden and returns a password question. The handler is invoked and must return HTTP 403 without calling the policy. This demonstrates that post-generation authorization still runs before content-policy handling.
- `testerQuestions_invalidStructure_doesNotCallCredentialPolicy` records policy calls, then returns a password question with an unexpected explanation field. It invokes the handler, expects HTTP 502, and asserts no policy call. Structural validation must reject that malformed envelope before the credential check sees it.
- `testerQuestions_nonSolicitingUrlCommandOrMarkup%s_isNotServerFiltered` runs three cases. Each fixture returns a question containing a harmless URL, `echo diagnostic`, or literal script tags; the handler must return HTTP 200 and the same question. This checks that no URL/command/markup detector was silently added to I4. The model is separately instructed not to produce such output.

The original successful-empty-result cases also run against the integrated policy. An empty list still returns HTTP 200 after one admitted attempt; the security extension does not convert it into a failure.

### Composed dependencies and prompt tests

These cases are in `src/test/developer-tester-questions-dependencies.test.ts`. Existing `setup()` mocks Supabase client construction, profile lookup, report/comment RPCs, the privileged quota RPC, and provider fetch. The local `request()` invokes the real default endpoint. `comment(1)` supplies a valid saved-comment shape so repository validation remains active rather than being replaced with a direct context stub.

- `developerDependencies_hardenedPrompt_keepsFakeAuthorityEncodedHiddenAndDiscussionEvidenceUnchanged` considers instructions planted in saved report text and another participant's discussion. It creates a description claiming SYSTEM/administrator authority and a comment containing a fake assistant role, an example destination, a harmless command, base64-looking text, a multilingual instruction, and hidden-span markup. The report RPC returns the modified description; the comment RPC returns that comment attributed to the reporter. The test invokes the endpoint and expects HTTP 200 using the existing benign mocked model answer. It extracts the provider fetch body, parses it, and requires two messages. The first must be a system message whose text addresses untrusted input, authority/roles, encoded and hidden content, credential categories, URLs, commands, and scripts. The injected description/comment must not be inserted into that system text. The second must be a user message whose parsed description and discussion exactly preserve the original strings and reply reference. It compares the whole message array with `testerQuestionMessages(context)`, asserts no tools/functions, and checks one fetch. For example, an embedded `https://example.invalid/submit` stays incident evidence in the user message; this test does not ask a live model to resist it.
- `developerDependencies_validJsonCredentialSolicitation_returnsOnlySafeFailureAfterOneProviderCall` replaces the provider fetch result with a valid chat-completions envelope whose content is JSON containing a browser question and `Can you paste your access token?`. It calls the default endpoint, expects HTTP 502 and only the safe unavailable body, then checks one fetch and one exact Developer quota RPC using the trusted actor ID. Unlike a malformed-output test, this proves the credential policy is reached through JSON decoding and the real composed generation path.

### UI failure and inert-text tests

These cases are in `src/test/developer-tester-questions-ui.test.ts`. Existing `setup(report, user, discussion)` renders the page with a mocked report repository and injected generator. `ready()` waits for the Comment textbox, `generateButton()` finds the explicit generation control, and `type(text)` changes manual composer text. `reloadDiscussion()` posts a normal manual follow-up so the existing successful-post behavior reloads comments. React Testing Library's `fireEvent` activates controls, its `findBy` queries wait for asynchronous updates, and `within(region)` limits checks to the assistant output.

- `testerQuestionsUi_policyRefusalDuringRegeneration_preservesPriorOutdatedQuestionComposerAndReply` starts with one discussion comment. It waits for the page, generates an initial accepted question, changes the mocked saved discussion to include an answer, and performs a manual follow-up to load it. After waiting for the outdated label, it selects the first comment's Reply control and types `Keep this manual reply`. It records how many manual posts have happened so later assertions distinguish earlier intentional posting from an unwanted assistant action. It then mocks current-session lookup and a safe HTTP 502 unavailable response, makes the next injected generator call the real browser client, clicks Generate again, and waits for failure feedback. The remaining assertions require the old question and outdated label, unchanged typed text, a cancel-reply control, enabled manual Post, and only the prior question's Copy control. Finally, it checks one fetch, unchanged manual-post count, and no lifecycle action. The scenario models the safe response produced by policy refusal; no rejected new question text enters the browser response or display.
- `testerQuestionsUi_mockedUrlCommandAndMarkup_areInertTextAndCopyRequiresExplicitAction` deliberately supplies three mocked questions containing an example URL, a harmless command reference, and literal script/image markup. It mocks fetch, window.open, and clipboard writes, waits for the page, types `Manual text`, clicks generation, and waits for the first result. It finds the assistant region and checks all three strings are visible literally. It requires no anchor, script, image, iframe, or form element inside that region. Clicking the URL-looking text must not fetch, open a window, copy, post, or invoke report lifecycle methods. Only after clicking `Copy question 3` does it expect feedback and one clipboard write containing the literal third string. It finally confirms unchanged manual text and no fetch/post. This tests inert React rendering and explicit manual action even for mocked output that violates the prompt-only URL/command guidance; it does not test that the server filters those categories.

## Test Cases Changed

- `testerQuestions_contextAtBoundPlus%d_hasExactAdmissionBoundary` in `src/test/developer-tester-questions-api.test.ts` keeps its two cases, `extra=0` and `extra=1`, and now imports `testerQuestionMessages`. The scenario is a saved context exactly at or one byte beyond the input guard after the prompt has been hardened. The test creates normal dependencies, clones the saved context, empties its description, and pads the description based on `MAX_QUESTION_CONTEXT_BYTES - questionContextByteLength(context) + extra`. It first checks the production byte helper's result. The new statement independently serializes the actual system/user messages with `JSON.stringify(testerQuestionMessages(context))` and counts UTF-8 bytes with `Buffer.byteLength`; that result must also be 60,000 or 60,001. The test then returns the padded context from the lookup, invokes the handler, and checks HTTP 200 with one quota/provider call at exactly 60,000 bytes or HTTP 413 with neither call at 60,001. The independent assertion prevents a stale estimate that omits the larger hardened instructions from appearing correct merely because the padding used the same helper.
