## Revision 2 implementation contract and ownership

The linked OpenSpec spec and design are authoritative. The implementer owns `src/features/auth/`, `src/shared/types/session.ts`, and `src/features/projects/types.ts`. The tester owns new `src/test/auth-*.test.ts` files. The coordinator owns `src/App.tsx`, this record, OpenSpec task checkboxes, `docs/developerGuide/Projects.md`, and any shared configuration. The documentation owner owns new auth guide topics, guide landing pages, and `_markbind/layouts/default.md`. Each owner preserves unrelated work in the shared tree.

`SessionUser` retains `{ id: string; username: string; displayName: string; role: 'tester' | 'developer' }`; project types re-export the shared type. `createAuthService(client: SupabaseClient): AuthService` exports `getCurrentSession(): Promise<Session | null>`, `signIn(email, password): Promise<void>`, `signOut(): Promise<void>`, `loadIdentity(authUserId): Promise<SessionUser>`, and `onAuthStateChange(callback): () => void`. `AuthError.code` is `invalid_credentials | incomplete_profile | unavailable`. The identity lookup only accepts an Auth ID, queries its matching protected profile, validates all fields, and never accepts caller roles. `AuthProvider` exports `useAuth(): AuthContextValue` with statuses `loading | signed_out | authenticated | incomplete_profile | unavailable`, nullable `user`, and `signIn`, `signOut`, `retry` actions. Only authenticated state carries a user. Later auth events supersede earlier lookups and session loss removes protected content immediately. Tests should use these public contracts and controlled Supabase responses; browser and isolated database verification are separate tasks.

The implementer and tester may proceed in parallel against this revision. Database migration is ordered before the pending project migration. `public.profiles(id, username, display_name, role)` is the sole identity table; no second Supabase client or identity schema is authorized. Existing simulation must remain development-only.

For Node-only lifecycle tests, the agreed implementation adds `src/features/auth/authSession.ts` exporting `AuthState` and `createAuthSession(service)`. The controller exposes `getSnapshot(): AuthState`, `subscribe(listener): () => void`, `start(): void`, `stop(): void`, `signIn(email, password): Promise<void>`, `signOut(): Promise<void>`, and `retry(): Promise<void>`. `AuthProvider` accepts `service: AuthService` and `children` props and presents the controller through `useAuth`. This is a testable lifecycle boundary with no new browser test dependency. The coordinator wires the production shared client in `src/App.tsx`.

Integration ownership clarification: the implementer also owns `src/features/auth/AuthenticatedApp.tsx`, which imports the existing shared client, constructs the service, and gates the normal-mode auth screens and protected identity view. The coordinator owns the guarded lazy import in `src/App.tsx` and the existing simulation-shell regression test. This keeps the simulated mode independent of Supabase configuration.

The user approved resolving a design omission: `AuthError.code` also includes `session_lost` for HTTP 401/expired-session profile rejections. The controller maps this outcome to signed out and clears protected identity. The coordinator updated the linked design at revision 5. Implementer and tester must reread the changed contract before their fix submissions. The local `.env` points to the actual Supabase project, so migration and integration permission checks must not run there; they remain pending an isolated project.

Acceptance: both roles log in with manually provisioned accounts; invalid credentials and service failures fail closed; missing/invalid profile shows the agreed setup message; restoration, retry, logout and session loss gate content and clear in-memory state; ordinary profile writes and anonymous reads are denied by the database. Public signup must be disabled in the Supabase dashboard. Inactivity timeout, account management, and project persistence remain outside this change. Required checks are targeted/full Vitest, lint, production build, documentation build, browser walkthrough, and isolated Supabase checks where an environment exists. Every implementer/tester submission and final combined state requires explicit reviewer approval before completion.
