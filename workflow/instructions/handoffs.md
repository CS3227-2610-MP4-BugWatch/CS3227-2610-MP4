# Completion Reports and Handoffs

Read before coordinating or carrying out a delegated task. For feature work, read the assigned plan and revision before editing; follow assigned file ownership and report contract changes to the coordinator.

### Completion Reports and Handoffs

For a new delegated assignment, use `workflow/templates/agent-assignment-template.md`. Supply the smallest sufficient context packet: task outcome, exact authoritative paths/revision, file ownership, agreed contracts, checks and expected return. Link supporting detail instead of repeating whole documents. This does not replace mandatory role references or prohibit retrieving additional relevant context; missing requirements must be resolved, not guessed. Evaluate completeness as well as size.

Implementation handoffs identify added/materially changed functions with a plain-language purpose, inputs/results, side effects, important failures/recovery and linked tests, following `workflow/templates/implementer-summary-template.md`. A compact handoff may link a function map rather than duplicate it; the final approved summary covers all relevant items. Test handoffs explain partitions, boundaries, negative cases and evidence levels as required by `workflow/instructions/testing.md`. Use complete sentences and a concrete example where it helps the user understand; do not invent executed checks.

For rendered UI work, the coordinator assigns `workflow/instructions/ui-evidence.md` and an owned visual-review report path. The UI polisher returns that record with captures and actual observations, or explicit unverified limitations. Reviewers assess the evidence and its revision as well as source changes. Static markup and successful builds cannot stand in for browser inspection.

Subagents return completion reports directly to the coordinator in their final response; separate report files are not required. Reports must identify the assigned plan and revision, completion status, changed files or reviewed scope, behaviour implemented or covered, actual verification commands and outcomes, and unresolved blockers, risks, or documentation needs. Reviewers also include actionable findings with supporting evidence, or explicitly state that no actionable findings were found and describe review limits.

Send blockers requiring coordination as soon as they arise rather than waiting for the completion report. The coordinator records concise handoff summaries and decisions in the feature plan under `workflow/<feature-name>/`, and includes significant outcomes in the overall log under `logs/`. Subagents must not edit the shared plan or create competing workflow logs. The implementer and tester each own only their assigned post-approval summary file in the same feature directory, using the relevant template under `workflow/templates/`. If another report artifact is necessary, the coordinator must explicitly assign a unique path and owner in that directory.

## Reviewer Approval of Completion

Every implementer, tester, or `ui_polisher` completion report, including reports after fixes or follow-up work, is a submission awaiting independent reviewer approval. Report the completed work and actual verification honestly; do not claim reviewer approval on your own behalf. The coordinator assigns each submission an identifier and sends every completion report, its plan revision when applicable, and the relevant work and verification state to the reviewer.

The reviewer must explicitly identify each reviewed submission and return `approved`, `changes_requested`, or `blocked`, with the reviewed scope and revision or state, supporting findings, verification limits, and unresolved requirements. A review may cover concurrent submissions together, but must state each submission's decision and whether the final combined implementation and tests are approved. Absence of findings alone is not approval.

Fixes and new implementer, tester, or `ui_polisher` completion reports require another review. Later edits affecting reviewed work invalidate the affected approval, including coordinator edits. The coordinator records decisions and resolutions in the plan, or in its task record and overall log if no plan exists, and must not complete the task until all latest submissions and the final combined implementation and tests have explicit approval against the final relevant state, findings are resolved, and applicable verification is satisfied. If review is unavailable or blocked, report the blocker and keep the task incomplete. Detailed tracking and re-review rules are in `workflow/instructions/coordinator.md`.

## Post-Approval Summaries

After the coordinator confirms independent approval of the latest submissions and combined work, each implementer or tester writes the unique summary file assigned to that agent in the feature directory. The usual filenames are `implementer-summary.md` and `tester-summary.md`; when multiple agents share a role, the coordinator adds an agent name to each filename. Each agent follows its own template in `workflow/templates/`, describes only its final reviewed work in plain language, and tells the coordinator the saved path. This summary-only acknowledgement is administrative; it is not a new implementation or test completion report. If application code or tests change after approval, report the change as a new submission for review and update the summary only after fresh approval.
