# Report development and Supabase handoff

The report feature supports Tester submission, private drafts, Developer acceptance and investigation, clarification state, fixed and non-fix resolutions, independent canonical-report links, shared discussion, a project-specific report listing, and authenticated readback through the shared Supabase client. See the [User Guide](../userGuide/Reports.md) for the workflows and field limits. The [project handoff](Projects.md) describes the prerequisite project and identity setup.

## Configure an isolated environment

Use an isolated test project, with Supabase Auth and the profile and project migrations `001` through `004` applied in order. Then apply `src/features/reports/database/005_reports.sql` followed by `src/features/reports/database/006_project_report_listing.sql`, checking which migrations have already been applied before running either. Migration `005` depends on `public.profiles`, `public.projects`, and the project trimming function; `006` depends on `005`. Provision a Tester and two Developers with matching profiles using the existing [account setup](Authentication.md) instructions. A Developer needs to create an active project for the browser walkthrough.

Set the application's Supabase URL and publishable key for the test environment as described in [project development](Projects.md). Never put a secret or service-role key in a `VITE_` variable. The project runner's ignored `.env.project-test.local` supplies the separate test URL, publishable key, isolated flag, and account emails; root `.env` must identify the separate production origin so the runner can reject it. The runner prompts for account passwords and the test-project elevated key.

Apply `src/features/reports/database/007_report_drafts.sql` after migration `006`, then `src/features/reports/database/008_report_workflow.sql` after `007`. Migration `008` adds the assignment timestamp, permits the Accepted and In progress states, extends workflow history and report reads, and adds the two workflow RPCs. Existing Open reports remain unassigned with a null assignment time. Provision a second Tester in the isolated database to verify draft ownership.

Apply the Tester assistant quota migrations `009_tester_suggestion_quota.sql` and `010_tester_suggestion_quota_five.sql` in order, as described in [Tester assistant](#tester-assistant). Then apply `src/features/reports/database/011_report_clarification_discussion.sql`. Migration `011` extends the allowed assigned states and history events, adds report comments and their scoped RPCs, and adds the waiting and resume actions. Existing reports and history remain available; existing reports begin with no discussion comments. Check the deployment sequence below before enabling the new actions on any shared environment.

Apply `src/features/reports/database/012_report_resolutions.sql` manually after `011` in the isolated test project's SQL editor. It adds nullable resolution and canonical-link columns, outcome and same-project reference constraints, Resolved/Closed compatibility, the two new history events, extended report readback, and resolution/link RPCs. Existing unfinished reports retain their state and assignment with no resolution or canonical link. The PowerShell verification runner does not apply migrations. Follow the reader-first deployment sequence below before enabling these actions in a shared environment.

## Architecture and boundaries

`src/features/reports/validation.ts` trims input and validates the required fields, explicit severity, and Unicode code-point limits. `reportRepository.ts` maps the application's camel-case contracts in `types.ts` to the report RPCs and converts failures into `ReportError` codes. `ReportCreatePage` loads active projects and owns submission; `ReportForm` owns field values and feedback. `ReportDetailsPage` reads a saved report, history, and conversation from `/reports/:reportId` and links back to its project's Reports tab. It keeps those read states separate so an activity or discussion read failure does not hide the report, and preserves unsent comment text across local tab changes and report readback. `ProjectReportsPanel` loads the project's list independently of the Overview and its history; the `?tab=reports` query selects that tab, while the project route defaults to Overview. The authenticated shell uses the existing shared Supabase client and rechecks authentication when a report operation reports an expired session.

The database remains the authorization boundary. `create_report` derives the actor from `auth.uid()`, requires a Tester profile, validates input, locks and checks the active project, and writes the report and creation history in one transaction. Callers cannot supply the reporter, state, assignment, ID, or timestamps. `get_report` and `get_report_history` provide report-scoped project and actor labels. `list_project_reports` returns summaries only for the requested project to authenticated users with profiles. Both roles can read submitted reports, but anonymous users and authenticated accounts without profiles cannot read them. Ordinary users have no direct report/history write grants; profile access is not broadened into a directory.

`accept_report(p_report_id)` and `start_report_investigation(p_report_id)` derive the actor from `auth.uid()` and require a Developer profile. Both lock the project before the report and reject an archived project under the lock. Acceptance requires an Open, unassigned report and atomically sets Accepted, the caller as assignee, and a server assignment time. The first acceptance wins; repeated or competing attempts return `P2006` without replacing ownership. Starting requires an Accepted report assigned to the caller, changes it to In progress, and preserves assignment and assignment time. A stale state returns `P2007`; a non-assignee is forbidden. Each transition and its corresponding history event are in the same transaction, so a history failure rolls back the report update. The RPCs are security-definer functions with an empty search path and authenticated-only execute grants; direct report and history writes remain unavailable to ordinary callers.

The report detail read returns assignment ID, time, username, and display name alongside state and existing report fields. The project listing returns assignment ID and scoped labels; assignment time remains detail-only. History reads retain creation entries and add acceptance and investigation entries with actor labels and before/after state; acceptance also records assignment identity and time. Labels are scoped to the requested report and rendered as text. Repository decoding rejects unsupported states and inconsistent assignment data. The authenticated wrapper applies existing session-expiry handling to both workflow methods. The detail page refreshes report and history after a successful action or conflict; after an uncertain result or failed readback, it offers read-only reload before another action.

`await_tester_information(p_report_id)` and `resume_report_investigation(p_report_id)` follow the same project-before-report lock order and derive the actor from the session. Only the assigned Developer can move an active-project report from In progress to Awaiting tester information or return it to In progress. The functions preserve assignment identity and time, update the report's timestamp, and commit the state change and one history entry together. A missing comment or reply does not prevent either action. A stale state returns `P2007`; a non-assignee, a missing profile, or an archived project is rejected at the database boundary.

`public.report_comments` stores an author, creation time, body, report ID, and optional reply target for each comment. The server derives author and time. A same-report foreign key prevents cross-report replies, and ordinary callers cannot directly write, edit, or delete comments. `post_report_comment` accepts a `jsonb` body parameter and checks that the incoming JSON value is a string before extracting text. It trims surrounding whitespace and rejects blank text or more than 5,000 Unicode code points; `validateCommentInput` applies the corresponding client-side validation. The authenticated Tester or Developer must have a valid profile and the project must be active. The function locks the project before the report, rechecks the reply target, and writes a comment without changing the report's state, assignment, update time, or workflow history. It does not create a separate clarification message type.

`list_report_comments` allows either authenticated role with a valid profile to read the report-scoped conversation, including when the project is archived. It returns a JSON array of at most 100 comments ordered by creation time and ID ascending. `reportRepository.ts` reads successive pages with the original timestamp and ID as a keyset cursor, preserving timestamp precision and rejecting malformed or non-advancing pages. The same authenticated wrapper used by existing report operations handles expired sessions for comment reads, posts, and clarification actions. Comment and identity text are rendered as text, not executable markup.

The project listing shows title, project, severity, state, assignee and reporter, newest first. The `list_project_reports` RPC returns one JSON array containing up to 100 reports, ordered by creation time and ID descending. Returning one value prevents a lower API row limit from silently shortening a page. The repository fetches successive pages using the original timestamp and ID as a keyset cursor so reports beyond the first page are included. A missing project returns `P2005`; an incomplete cursor returns `P2003`. The timestamp is retained at its database precision for ordering.

Drafts and submission receipts live in separate tables. Owner-scoped RPCs require an authenticated Tester profile and check the target project's archive status at save and submit time. Draft submission creates the report and its history, records the receipt, and consumes the draft in one transaction. A retry with the same draft ID can return the report already created for that author. Draft routes use the authenticated data router for the unsaved-navigation warning, and the Vercel rewrite serves the app on direct draft URLs.

### Resolution and canonical-link contracts

The detail UI shows canonical selection, loading/retry feedback, and **Save canonical link** only inside the open resolution form with **Duplicate** selected. Link saving remains an explicit non-submitting button before resolution; there is no standalone link section or nested form. Existing canonical readback remains visible to both roles. The RPC still supports independent link persistence under its existing authorization rules; UI visibility does not change those database contracts.

`ResolutionInput` in `types.ts` is discriminated by `kind`. `fixed` requires `fixSummary`, `affectedVersion`, `commitUrl`, and `pullRequestUrl`; `duplicate` requires `explanation` and `canonicalReportId`; `invalid`, `cannot_reproduce`, and `will_not_fix` require only `explanation`. `ReportResolution` adds derived author ID, scoped nullable identity labels, and server resolution time. `Report.resolution` is nullable; `Report.canonicalReport` is the independently saved current `{ id, title }` target. Duplicate resolution retains a separate captured canonical ID, so later link changes cannot rewrite its resolution or history snapshot.

`validateResolutionInput` trims surrounding whitespace, counts Unicode code points, rejects invalid runtime types and inapplicable fields, and returns normalized input or typed `ResolutionFieldErrors`. Summary/explanation limits are 1–5,000, affected version is 1–100, and each required fix URL is at most 2,048. URLs must be absolute HTTP(S) destinations with a host, with no provider or project-host restriction. URL validation does not fetch the destination. Trusted RPC validation repeats the relevant checks using the existing project trimming and URL validation functions.

`resolveReport(id, input)` calls `resolve_report(p_report_id uuid, p_resolution jsonb)`, converting only applicable fields to snake_case JSON. The RPC derives the actor from `auth.uid()`, requires the assigned Developer and an active project, locks the project before the source report, and rechecks In progress under the lock. Duplicate resolution requires a valid persisted canonical link matching the requested target; an unseen replacement returns `P2007`. It atomically saves Resolved state, normalized fields, author/time, update time, and one `resolved` history event containing the state transition and full immutable resolution snapshot. It preserves assignment identity/time and the original submitted report version.

`linkDuplicate(id, canonicalReportId, expectedCanonicalReportId)` calls `link_duplicate_report(p_report_id uuid, p_canonical_report_id uuid, p_expected_canonical_report_id uuid)`. It uses the same role, assignee, archive, and lock checks without changing state. The target must be another submitted report in the same project; Resolved and Closed targets remain eligible. Composite foreign keys and self-reference checks protect both current and captured targets. Changed links compare the expected current ID under the lock, then atomically save the target/update time and one `duplicate_linked` event with old/new IDs. Saving the existing target is a no-op, including timestamps and history. Linking never changes the target report or an existing resolution. No unlink or close RPC is provided.

Both mutations return authoritative `get_report` readback and never retry automatically. They retain the existing error mapping: `P2001` authentication, `P2002` permission, `P2003` validation, `P2004` archive, `P2005` missing source, and `P2007` stale state/link. Invalid targets return validation without exposing private drafts. Ordinary direct report/history writes remain unavailable. Both mutation methods are wrapped by `AuthenticatedApp` session handling.

Strict repository readers support Resolved and Closed, validate outcome fields and metadata, and retain old history variants. Pre-migration unfinished wire records may omit the new fields and decode them as null; Resolved/Closed records require valid resolution data. Detail reads and consumed-draft receipts share this support, while project summaries retain their existing state and assignment presentation. The detail page uses the complete paginated `listProjectReports` result for canonical choices and excludes the source. Selector read errors remain separate from readable report data. Resolution, linking, commenting, and other workflow writes share the pending guard; successful saves and conflicts refresh report/history, and uncertain outcomes require read-only reload. Generation checks discard completions after report or identity replacement. Both roles can read resolution and links, including archived reports; comments remain available on active Resolved reports.

### Deploy compatible readers before enabling actions

Coordinate migration `011` and the compatible frontend so that older clients cannot encounter the new state or history events. Deploy compatible readers before enabling clarification actions; use a maintenance window if the reader and migration deployment cannot be coordinated safely. If rollback is needed, disable the new mutation entry points while retaining comments, waiting states, history, and readers that support them. Do not revert to an older state decoder or drop stored workflow or discussion data. Use a forward corrective migration where needed.

For migration `012`, stage a compatible-reader release before the schema and action release. That first release must read the new states, resolution metadata, history events, listings, and draft receipts while leaving resolution/link actions disabled. Apply and verify `012` in the isolated project, then deploy the tested schema through the authorized database process and release the new controls. The migration grants authenticated execution of its new RPCs, so deploy compatible readers before applying it to a shared target. Do not expose new writes to old readers.

Rollback by disabling the new controls or revoking execution of `resolve_report(uuid,jsonb)` and `link_duplicate_report(uuid,uuid,uuid)`, while retaining compatible readers and recorded resolution/link/history data. Do not revert to readers that reject Resolved or Closed, delete records, or drop columns as a routine rollback. Use a forward corrective migration; a destructive downgrade needs a separately reviewed data-preservation plan.

## Tester assistant

For local development, fill the ignored `.env` or `.env.local` from `.env.example` and run `npm run dev`. Vite's development middleware runs the existing suggestion endpoint at `/api/tester/report-suggestions` on the same local address as the app. Restart the dev server after editing env settings. The middleware loads the server keys into the Node process and exposes only Vite's normal public variables to browser code.

The middleware applies only to Vite's development server. Vercel uses `npm run build` for the frontend and runs `api/tester/report-suggestions.ts` as a function, using the project environment settings. Set the keys separately for the review deployment. Local files supply local development values.

Apply `src/features/reports/database/009_tester_suggestion_quota.sql` after `008` in the isolated database, then apply `010_tester_suggestion_quota_five.sql` to raise the limit to five attempts per rolling five minutes. Migration `010` preserves existing attempt timestamps and updates both the quota function and storage constraint. Apply both migrations for a fresh database; apply only `010` if `009` is already installed. The quota function can be invoked by the server's service role. It checks the Tester profile and serializes requests per Tester using a row lock and database time. Only the latest admitted timestamps are needed.

To verify the quota migrations in disposable PostgreSQL, set `QUOTA_TEST_DOCKER=true` and `QUOTA_TEST_DOCKER_PATH` to your Docker executable, then run `npm run test -- --run src/test/report-suggestion-quota.test.ts`. Docker must be running. This opt-in suite uses `postgres:17.6-alpine3.22`, checks upgrade preservation, the sixth-attempt limit, expiry, concurrent requests and permissions, and removes its temporary container afterward. It does not connect to hosted Supabase.

The form calls `POST /api/tester/report-suggestions` with the current Supabase bearer token. The Vercel Function verifies the session and exact `tester` role, loads the active project through the user's authorized Supabase client, and reserves quota before contacting SoCLaaS. It forwards only allowed form fields and the server-looked-up project name and description. Severity and the project ID stay in BugWatch. The provider request disables reasoning with `reasoning_effort: 'none'` so the configured Qwen model can return its JSON answer within the 1,500-token output budget and 15-second timeout. The endpoint filters malformed suggestion and question entries and returns a safe error when no entries are usable.

Keep `TESTER_SUGGESTIONS_ENABLED` disabled until the live model, account quota handling and retention are confirmed. For isolated preview setup, configure the function's `SOCLAAS_API_KEY`, `SOCLAAS_MODEL`, and `SUPABASE_SERVICE_ROLE_KEY` as server settings. The server reuses `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` from the frontend. The earlier server names are accepted as a fallback. Use a service-role key from that same isolated project. Keep both secret keys outside `VITE_` variables. Mocked tests exercise the contract without contacting SoCLaaS.

## Verification

Run local checks from the repository root:

```sh
npm run test -- --run
npm run lint
npm run build
npm run docs:build
```

The ordinary suite skips hosted database tests when isolated settings are absent. To run the report database suite with the isolated setup above on Windows, use:

```powershell
npm run test:report-db
```

This selects `src/test/report-database.test.ts`, `src/test/report-workflow-database.test.ts`, `src/test/report-discussion-database.test.ts`, and `src/test/report-resolution-database.test.ts` through `run-project-db-tests.ps1`; it obtains fresh Tester and two Developer tokens and restores process environment values afterward. First apply migrations through `012` manually, only to the separately configured isolated project. The suites create temporary projects, reports, comments, and an Auth user without a profile, then remove their fixtures. Fixture setup and cleanup require the test-project elevated key. Resolution permission assertions use ordinary clients and cover permitted outcomes, invalid targets, direct-write denial, archive/state/assignment rejection, stale links, immutable snapshots, and competing resolution/clarification/link requests. A skipped hosted suite is not a hosted pass.

To run transactional resolution/link failure-injection checks as well as the report integration suites, install PostgreSQL `psql` on `PATH` and add the isolated connection settings to the ignored `.env.project-test.local`:

```text
PROJECT_TEST_DATABASE_HOST=db.<test-project-ref>.supabase.co
PROJECT_TEST_DATABASE_USER=postgres
PROJECT_TEST_DATABASE_PORT=5432
```

Use the connection details from the isolated project's database settings. A Supabase pooler host ending in `.pooler.supabase.com` is also accepted with user `postgres.<test-project-ref>` and its configured port. The runner checks that the connection identifies the same project as the isolated Supabase URL; it rejects an unrelated direct host or user. The port is optional and defaults to `5432`. The database is fixed to `postgres`, and SSL is required. Do not put a password in these settings or in the command line. Run:

```powershell
npm run test:report-db -- -VerifyResolutionSql
```

Equivalently, run `./run-project-db-tests.ps1 -Suite report -VerifyResolutionSql` from PowerShell. The runner prompts securely for the isolated database password, which is distinct from the service-role key, runs `verify_report_resolutions.sql` with `psql`, then runs the selected Vitest suites. It restores connection environment values afterward. It never applies `012` or any other migration; apply the migration manually before this command. The flag is valid only for the report suite. Without the flag, the runner needs no direct database connection and runs only the integration suites.

After applying migrations `005` and `006` in the isolated test project, run `src/features/reports/database/verify_report_transactions.sql` in that project's SQL editor. It creates transaction-local fixtures and forces a history write failure to check rollback; its final statement rolls the transaction back. Do not run the fixture script against production.

After applying migration `007`, run `src/features/reports/database/verify_report_drafts.sql` in the isolated test project's SQL editor. It checks ownership, archived-project rejection, reassignment, rollback, and repeated submission. The script rolls back its fixtures.

After applying migration `008`, run `src/features/reports/database/verify_report_workflow.sql` in the isolated test project's SQL editor. It forces history writes to fail for acceptance and investigation, checks that each report update and its event roll back together, and rolls back its final fixtures. Run the script only against the isolated project.

After applying migration `011`, run `src/features/reports/database/verify_report_clarification_discussion.sql` in the isolated test project's SQL editor. It forces each clarification history write to fail and checks that the associated report change rolls back. It also checks waiting without a comment, resuming without a reply, and discussion independence. The final statement rolls back the fixtures and verification trigger; do not run the script against production.

After manually applying `012`, run `src/features/reports/database/verify_report_resolutions.sql` as the isolated database administrator, either in its SQL editor or through the optional runner flag above. It injects history failures for Fixed and Duplicate resolution, initial linking, and replacement linking, and checks that report fields, state, assignment, links, timestamps, target data, and event counts remain unchanged. It also checks an unchanged-link no-op and a successful replacement that preserves the captured Duplicate target. The final `rollback` removes fixtures and the test trigger. These transactional checks complement ordinary-client permission and concurrency tests; mocked RPC tests cannot prove rollback or locking.

For a browser walkthrough, sign in as a Tester, open an active project, select **Report bug**, submit valid information, and reload the saved report link. Use **Back to project reports** to open the project's listing and the **Project** link in the report facts to open its Overview; check report ordering and retry behaviour. Check missing and overlong fields, unselected severity, project loading errors, cancellation, and retained input after a recoverable failure. With two Developers, verify detail-only acceptance, a competing acceptance conflict, assignee-only investigation start, persisted assignment and activity after reload, and labels in the listing. As the assigned Developer, enter Awaiting tester information before writing a question, post it, and have the Tester reply; verify the reply leaves the state waiting until the Developer resumes investigation. Check the chronological reply link, compact Activity changes, section retries, and retained unsent text when switching tabs. Check that the Tester can read the result and neither role can post or take workflow actions on an archived project. Confirm Developers cannot create reports and existing drafts and navigation still work. Use isolated accounts and data. The repository's automated checks do not by themselves establish that a hosted migration or browser walkthrough passed.

For resolution review, use separate In progress reports for each outcome. As the assigned Developer, open **Resolve report**, check the editable affected-version prefill, both mandatory URLs, validation boundaries, cancellation, and each non-fix explanation. Select Duplicate and save its canonical link within the resolution form before saving the resolution, confirming that the link save changes no state. Check that canonical controls are absent before opening resolution, for other outcomes, after cancelling, and after resolution. Include Resolved and privileged Closed target fixtures in the isolated project, exclude the source and private drafts, and verify post-resolution link replacement through the unchanged isolated RPC suite or a prepared fixture to confirm that its captured target remains unchanged; this replacement is not available through the resolution UI. Reload as both Developer and Tester and inspect resolution values, author/time, original version, assignment, project listing, and both new Activity disclosures. Confirm there are no Developer close/reopen/retest controls and active Resolved discussion still works.

In separate tabs, exercise competing resolution/clarification requests and a stale canonical-link replacement; check the conflict refresh and unchanged winner. Test uncertainty by interrupting a save/readback, then use read-only **Reload** before another attempt, checking that mutations are not retried automatically and applicable text is retained while on the page. Check expiry/navigation during pending requests, archived read-only details, keyboard labels/focus/error associations, narrow layouts, and long URLs or markup-like text. Hosted migration checks and this two-role walkthrough are manual review steps: record their actual results separately rather than treating local test passes or skipped integrations as evidence that they ran.
